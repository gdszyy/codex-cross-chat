# Codex 跨设备对话通信方案

版本：V1.0　日期：2026-10-09　用途：方案讨论与后续开发依据

## 1. 方案结论

建议采用“Railway 消息中转服务＋每台设备的本地桥接程序＋Codex 通信工具”的架构，让不同设备上的指定 Codex 对话能够互相派发任务、询问进度和回传结果。

Railway 负责保存、寻址和传递消息。任务仍在目标设备的 Codex 环境中运行，使用该设备的项目文件、模型配置与现有权限。两端无需处于同一局域网；本地桥接主动向云端建立连接。

首版面向同一使用者管理的两台设备，只接入明确登记的对话。推荐先实现一次完整往返：A 对话发送任务 → B 对话处理 → 结果回到 A 原对话。双方均可作为发起方。

本方案处于设计阶段。官方接口和平台能力提供可行性基础；现有桌面对话能否被安全恢复、运行中如何协调、回复能否在桌面正确显示，必须经过对应版本的实测。不能把“API 调用成功”直接解释为“跨设备桌面对话已打通”。

## 2. 目标与首版范围

### 2.1 使用场景

- 跨设备分工：电脑 A 的主对话让电脑 B 的测试对话运行验证，B 返回结果和证据入口。
- 跨设备询问：A 向 B 的指定对话询问某项任务的现状，B 基于自己的上下文回答。
- 跨设备回报：B 执行完成后，自动把结果送回已绑定的 A 对话，无需用户复制粘贴。
- 离线暂存：B 离线时保留未过期消息，恢复连接后继续投递；A 离线时同样暂存返回结果。

### 2.2 首版交付边界

| 纳入首版 | 首版不承诺 |
| --- | --- |
| 两台设备注册、设备撤销、在线状态 | 设备关机后仍在该设备执行任务 |
| 指定对话登记、精确发送、状态查询 | 任意对话自动发现并开放访问 |
| 文本任务、必要背景、结果与证据引用 | 整段历史实时镜像、全部文件同步 |
| 离线排队、过期、取消、重复投递去重 | 分布式环境下绝对“恰好执行一次” |
| 每个对话串行接收、最终结果回传 | 自动跨设备搬迁正在运行的任务 |
| 最小状态页或命令入口 | 多租户团队平台、复杂调度与计费系统 |

代码继续使用 Git 协作。任务消息可带仓库、分支、提交和报告位置；接收方先核实本地版本。未提交文件和本机绝对路径不会因消息发送而自动成为对方可用的资源。

## 3. 整体架构与职责

通信路径：设备 A 的 Codex 对话 ↔ A 本地桥接 ↔ Railway 消息服务 ↔ B 本地桥接 ↔ 设备 B 的 Codex 对话。

### 3.1 Railway 消息服务

云端保存设备身份、已开放对话的路由、消息正文、投递状态与执行回执。消息落入数据库后才返回“已接收”。目标离线时保留消息；重连时按游标补发尚未确认的数据。

建议首版使用一个常驻后端服务和一个 PostgreSQL 数据库。HTTP 接口负责发送、查询和取消；WebSocket 负责设备连接与事件推送。数据库是消息状态的事实源，WebSocket 仅承担实时传输。

Railway 官方文档说明其支持持久运行的服务、PostgreSQL 部署以及基于 HTTP/1.1 的 WebSocket，可作为此架构的托管基础。[2][3][4] 实际账户套餐、区域、配额与费用在部署前核实。

### 3.2 每台设备的本地桥接程序

桥接程序主动连接 Railway，接收消息后先检查来源、目标和任务授权，再通过本机可用的 Codex 接口投递。它记录消息与实际执行轮次的对应关系，采集完成、失败、中断和待用户处理的状态，负责回传。

本地使用独立小型数据库或持久日志记录接收、启动与回传进度。它不修改 Codex 会话数据库，不复制登录凭证到云端，也不把任意远端指令直接当成系统命令执行。

每个桥接实例只管理自己登记的对话。云端短暂不可用时，本地已启动任务可继续运行，最终结果保存在本地待发送队列，网络恢复后补传。

### 3.3 Codex 通信入口

向已接入的 Codex 提供一组受控工具：列出允许联系的目标、发送任务、查询状态、读取结果和请求取消。首版建议用本地 MCP 工具适配桥接程序；工具实现时核验调用所属对话，不能只相信模型自行填写的发送者身份。

技能或提示规则用于说明何时使用工具、如何交付结果。单独安装技能或连接云端 MCP 不足以保证闲置的本地对话被唤醒，仍需要桥接程序负责接收和启动。

### 3.4 Codex 接入原则

官方 App Server 提供线程读取、恢复、轮次启动和事件接口，可作为桥接适配层的基础。[1] 本机现有 messenger 脚本中也存在 thread/resume、turn/start 的调用，但本轮只检查了实现入口，未运行发送测试。

优先使用受支持的本地通道；桥接到云端的 WebSocket 是本方案自行实现的传输层。官方 App Server 的 TCP WebSocket 目前标为实验性，不作为首版公网入口。[1]

特别注意：另启一个 App Server 并读取相同历史，不等于接管桌面中正在运行的会话。必须先验证桌面与桥接对同一线程的所有权和并发行为。若无法安全协调，首轮仅使用明确交由桥接控制的空闲测试对话；未经证明，不开放普通活跃对话的自动写入。

## 4. 一条消息如何完成往返

以下是推荐流程，包含自动回报所需的完整链路。

1. A 的通信工具提交目标设备、目标对话、任务正文、必要背景、结果要求和有效期。目标必须来自已授权目录，不按相似标题猜测。
2. A 桥接验证调用身份和允许范围。Railway 校验路由后持久化消息，生成唯一消息编号，返回“已入队”。
3. B 在线时领取消息；B 桥接先把它写入本地接收记录，再确认“设备已收到”。这一步不代表 Codex 已执行。
4. B 桥接确认目标对话可安全接入且空闲后投递，保存实际 threadId、turnId。忙碌时排队；不默认中断或重定向现有任务。
5. B 在现有权限下处理任务。遇到审批、登录、权限拒绝或材料不足时返回具体状态；桥接不自动替用户批准。
6. B 桥接读取该轮次真实终态及最终输出，打包为结果消息，包含原请求编号、结论、验证、剩余事项和可访问的证据引用。
7. Railway 保存结果，并按原请求绑定的回程地址投递给 A。A 桥接确认落盘后，在原对话可安全接入时追加一条带来源的结果通知。
8. A 的原对话读取并处理报告。系统分别记录“结果已保存”“已送达原对话”“已被接收方处理”；任务业务验收另由接收方或用户判断。

B 的完成通知只回到原请求绑定的对话，不能由回复正文任意改写接收人。结果通知本身不要求自动回信；若确需后续协作，应由 A 在原授权范围内另发明确请求。

## 5. 消息、状态与恢复规则

### 5.1 最小数据结构

| 对象 | 建议保留的信息 | 作用 |
| --- | --- | --- |
| 设备 | 所有者、设备编号、凭证状态、最后连接时间 | 身份校验与撤销 |
| 对话路由 | 设备、运行环境/profile、threadId、展示别名、允许来源 | 精确寻址，避免同名误投 |
| 请求 | 消息编号、来源与目标、类型、正文、有效期、关联任务、回程地址 | 投递、去重与追溯 |
| 执行记录 | 消息编号、实际 turnId、启动记录、执行状态、错误原因 | 将网络消息对应到真实执行 |
| 结果与回执 | 原请求编号、最终输出、证据引用、目标接收状态 | 完成双向闭环 |

云端与本地都要保留唯一消息编号；网络重试沿用原编号。设备编号由注册关系校验，threadId 只能定位到其所属运行环境，不能脱离设备和 profile 单独当作全局地址。

### 5.2 状态必须分层

- 投递状态：已入队、设备已接收、已过期、投递被拒绝。
- 执行状态：待启动、运行中、等待用户、已完成、失败、已中断、结果待核对。
- 回传状态：本地结果已保存、云端结果已保存、已送达原对话、接收方已处理。

“设备离线”是连接状态，不直接把运行中的任务判为失败。进程完成但没有预期报告时，保留执行终态，同时标记结果缺失，不能将其显示为业务完成。

### 5.3 防止重复执行

正常路径采用可重试投递与本地去重：同一消息即使收到多次，也只对应既有执行记录。接收端启动前先写启动意图，取得 turnId 后立即保存，重连优先查询原轮次。

仍存在一个需要显式处理的窗口：Codex 已接受启动，但桥接在保存 turnId 之前崩溃。恢复时应结合消息关联标记和线程历史查找原轮次；无法唯一确认时进入“结果待核对”，暂停该请求自动重启。消息标记只是核对线索，不能当作官方提供的幂等保证。

本方案不承诺任务副作用恰好一次。涉及代码写入或外部操作的请求，不允许仅因超时就换新编号重发。

### 5.4 排队、取消与循环控制

同一对话串行处理；不同对话在各自环境允许时可以并行。首版单设备只有一个桥接写入实例；桌面的人工操作不受桥接自己的队列锁约束，因此仍需完成第 3.4 节的所有权验证。

尚未启动的请求可取消。已运行请求只发送中断请求，直到读取到真实终态才显示“已中断”；已发生的文件和外部操作不会因此回滚。取消与完成同时发生时，以实际轮次状态为准。取消来源请求后，迟到结果仍可归档，但不自动重新启动来源对话。

禁止默认广播、自动转派和“谢谢→不客气”式循环。每个任务链设置有限的自动续轮上限，重复结果去重；超过范围或预算时报告状态，由既有主责决定下一步。

## 6. 权限与资料边界

跨设备来信可能启动本地工具执行，必须把设备身份、对话许可和任务授权一起校验。

- 设备接入：每台设备使用独立可撤销凭证；撤销后立即阻止新领取和新投递，并关闭对应连接。
- 对话开放：默认只公布别名和必要状态，只有登记的对话及允许来源可收发；不公开全部历史。
- 权限继承：目标任务继续遵守本机沙箱、审批和项目边界。远端正文不能修改这些规则，也不能自行取得执行权限。
- 来源展示：消息显示设备、来源对话和原请求关系；附件、引用内容和外部文本保留其数据属性。
- 凭证保管：模型登录、API 密钥和认证文件留在各自设备；Railway 只保存消息服务自身的凭证配置。
- 数据保留：首版按“中转服务能够读取消息正文”设计，不宣称端到端加密。传输使用 TLS；建议正文保留 7 天、状态元数据保留 30 天，支持主动删除。备份过期与删除生效时间须在实施时一起定义。

上述保留期是可调整的方案默认值。实际部署前应确认允许通过 Railway 中转的资料类别；既有模型服务的数据授权不会自动等同于新增托管平台的资料授权。

首版正文建议限制为 64 KB，仅传任务所需内容。大文件采用已有授权位置的链接或 Git 引用，不上传整个 .codex、项目目录或完整对话历史。不可访问的证据引用必须明确标记，不能只给对方一个本机路径就算交付。

## 7. 部署、运行与成本

### 7.1 推荐部署组成

| 位置 | 首版建议 | 运维要求 |
| --- | --- | --- |
| Railway | 一个常驻消息服务，优先单实例 | HTTPS/WSS、健康检查、平滑停机、重连恢复 |
| Railway | 一个 PostgreSQL 服务 | 保存消息和状态，配置备份并做恢复演练 |
| 设备 A、B | 各一个桥接进程和本地状态库 | 登录后运行、断线恢复、状态可见、可手动停止 |
| 各 Codex 环境 | 通信工具与使用规则 | 固定兼容版本范围，升级后做接入回归 |

消息服务建议采用 TypeScript/Node.js，便于统一接口与事件类型；如现有维护者更熟悉 Python，可用等价实现，不影响架构。首版用数据库承载待投递记录，无须增加 Redis 或专门消息队列。

服务应配置为常驻运行，核对 Railway 的 Serverless/休眠设置，避免设备无人操作时影响投递及时性。[5] 部署重启会断开连接，因此重连和持久化必须作为正常路径设计。

### 7.2 建议运行参数

起始参数为：连接心跳 30 秒、连续 90 秒无响应显示离线、重连采用指数退避并限制单次间隔至 60 秒、未启动请求默认 24 小时过期。它们是工程建议值，不是平台保证或实测性能。

请求有效期只限制“何时还可以开始”，运行中的任务不因该有效期到点而假定终止。执行时限另行设置，到期报告并按已授权规则请求中断，真实停止仍须确认。

记录连接断开原因、请求编号、执行轮次、关键时间点和错误类别；默认不把正文和凭证写入普通日志。状态页至少能显示设备在线情况、积压、待用户处理、结果待核对与失败请求。

### 7.3 成本口径

成本由云端后端运行、数据库与备份、网络流量、本机资源及各 Codex 环境的模型使用组成。中转服务自身无需再调用模型；任务和回传后来源对话的处理仍可能消耗模型额度。

当前不提供未经核实的月费数字。部署前按实际套餐和资源上限估算，试运行后用真实用量校准；对自动续轮和日志保留设置上限。服务重启不能丢失任务，是比首版横向扩容更优先的目标。

## 8. 实施顺序与验收标准

以下是后续实施建议，本轮交付止于方案文档。

### 8.1 先验证本地接入，再建设云端闭环

1. 本地兼容验证：在每台设备记录 Codex 版本、profile 和接入方式，用指定测试对话验证读取、恢复、启动、最终结果和桌面可见性。检验桌面与桥接并发，不能可靠串行则保留阻断，不扩展至活跃对话。
2. 双机闭环：部署最小中转与数据库，接入两端桥接，让 A 发送请求、B 执行、结果回到 A 原对话；再反向执行一遍。
3. 恢复验证：覆盖断线、重复消息、启动窗口崩溃、忙碌排队、取消、审批、设备撤销和中转服务重启。
4. 小范围使用：仅登记已验证的对话，观察真实任务；形成安装、停止、升级与故障恢复说明后，再考虑增加设备。

### 8.2 必验用例

| 验证情形 | 可接受结果 | 需要保存的证据 |
| --- | --- | --- |
| A → B → A 和反向往返 | 回复进入准确的原对话，保留请求关系 | 双方消息、turnId、原对话回读 |
| 两个对话名称相同 | 按登记标识精确投递，不按标题猜测 | 路由记录和接收线程 |
| 接收设备离线后上线 | 未过期消息恢复投递，过期消息不启动 | 连接时间、队列记录、执行次数 |
| 来源设备离线 | 结果持久保存，上线后回到原对话 | 本地与云端结果记录、回读 |
| 同一请求重复投递 | 对应同一执行记录，不产生第二次启动 | 重复投递日志、轮次列表 |
| 启动后回执丢失或桥接崩溃 | 查回原轮次；不确定时停在待核对 | 崩溃注入记录、恢复结果 |
| 对话忙碌或桌面人工输入 | 安全排队或明确拒绝，不抢写历史 | 运行事件、历史完整性核对 |
| 宿主审批、凭证失效、权限拒绝 | 显示具体待处理或失败，不自动绕过 | 宿主状态和云端对应状态 |
| 设备凭证撤销、伪造来源 | 拒绝新请求，无法读取或控制其他对话 | 拒绝回执、无新增轮次 |
| 取消与执行完成并发 | 保留真实终态，不声称已撤销副作用 | 取消请求与实际轮次终态 |
| Railway 服务重启、数据库短暂不可用 | 已确认入队消息不丢；数据库未写成不回成功 | 重启前后消息核对 |
| 最终结果重复或执行无报告 | 结果不循环触发；缺报告明确可见 | 原对话通知次数、缺失状态 |

验收必须穿过真实通信工具、Railway、两端桥接及 Codex 原对话。仅测试 HTTP 通、数据库有记录或 CLI 输出成功，都不足以判定跨设备对话可用。

### 8.3 实施前需要明确的事项

首轮建议采用“同一使用者、两台设备、指定测试对话、文本消息”的范围。实施前登记设备操作系统、Codex 版本与认证方式，明确可中转资料类别、Railway 账户与预算，以及本地桥接运行方式。已有授权可复用，仅对真实缺口补充决定。

若桌面线程格式无法由官方接口安全处理，应明确记录“不支持当前版本接入”，而不是编辑会话数据库。使用新建桥接专用对话只可作为单独验证路径，不能冒充原有桌面对话兼容性通过。
