## 2. 阻断发现（4 条）

### 阻断 1｜标记证明对目标群体失效，且「已具备实测基础」是跨版本过度声明

- **重算事实**：设计把标记证明当作**已成立**的登记/重绑机制——`mechanism-design.md:47`："**标记证明（登记与重绑时用，已具备实测基础）**…桥接用 `thread/list`（近期、`useStateDbOnly`）＋`thread/read`（末轮）扫描，标记唯一出现在哪个线程，哪个线程就是本对话…两条 M1 实测支撑此路径"；附录 `:355` 把「`thread/read` 末轮回读可用」列为可行基础。
- **该实测的可证面**：这两条实测（`m1-compat-report.md:84` 行 4 `thread/read` 轮询终态、`:87` 行 7 `thread/list`）**只发生在探针自建线程上**；该线程 `historyMode="legacy"`、`cliVersion="0.149.0"`（`as-list-default.json` 首条，我现算）。
- **失效链**：标记要写进目标线程的**下一条回复**，桥接须 `thread/read`（`includeTurns:true`）回读到它；对 14 个目标线程（`paginated`／`0.153.4`），这正是官方判为 **fail closed** 的 "full-history reads / turn pagination"。⇒ 扫描命中 0（偶发命中多）→ 按 `mechanism-design.md:102` "命中 0 个或多个 → fail-closed，转人工确认（Owner 从近期线程列表里点选）"。**登记与重绑对目标群体退化为人工点选**，「谁能让某随机串出现在某线程里，谁就拥有该线程」的**能力证明前提不成立**。
- **定级**：把「0.149.0 自建 legacy 线程可读」写成对 14/14 目标线程也成立的「已具备实测基础」，属**事实级过度声明**（同 `REVIEW-M1` 阻断 1／事实错误一体两面）。**阻断。**

### 阻断 2｜版本错配被静默假设：设计从不区分 0.149.0 与 0.153.4

- **重算事实**：设计唯一提到版本的位置是附录 `mechanism-design.md:357`："`codex app-server --stdio` 全链路（start/resume/turn/read）本机可用，**CLI 0.149.0**——compat §2/§4（桥接本机通道选型）"；全文无 `0.153.4`。
- **错配**：桌面后端实际是 `0.153.4`（`REVIEW-M1.md:38`–`40`；`env-recon.txt` 第 30 行进程路径互证），既有线程也由 `0.153.4` 建（`as-list-default.json` 现算 14/14）。设计把 0.149.0 上测得的 `thread/list`＋`thread/read`＋`resume` 行为，**默认对 0.153.4 的会话库同形**——这正是 M1 复核点为「环境清单事实错误」的同一错配，设计未承接。
- **影响面**：阻断 1 的标记证明、`mechanism-design.md:197` 的 push 投递、`:102` 的重绑，全部建立在被静默假设的接口行为上。**阻断。**

### 阻断 3｜§5.4 pull/push 对既有桌面对话都不闭环，且与方案 §3.3 明文冲突

- **设计断言**：`mechanism-design.md:197`「pull（桌面手开对话）：桥接**不写**该线程；任务与结果存服务端收件箱，对话**下次自然醒来（人或工具触发）**时 `relay_inbox` 读到全部待办」；`:198`「此分档让『桌面对话参与协作』**不必等并发写验证通过**」。
- **冲突原文**：`plan-v1.md:61`（§3.3）"单独安装技能或连接云端 MCP **不足以保证闲置的本地对话被唤醒**，仍需要**桥接程序负责接收和启动**。"⇒ 方案明确：唤醒源只能是桥接；而 pull 的定义恰是**桥接不写该线程**。故 pull 模式**没有唤醒源**：`relay_inbox` 需对话已在运行才能被调，"工具触发"未定义具体机制。
- **push 侧同样不通**：`:196` push ＝"桥接确认线程空闲后起轮次投递"，起轮次须 `thread/resume`／`turn/start`，对 `paginated` 线程**官方 fail closed**（同阻断 1 证据）⇒ 对既有桌面对话 push 也不可用。
- **后果**：对**目标群体（既有桌面对话）**，push/pull 两条投递路**都不闭环**；`:198`「不必等并发写验证通过」的结论不成立；`plan-v1.md:21`（§2.1「跨设备回报…无需用户复制粘贴」）落空且设计未披露。**阻断。**

### 阻断 4｜票据兜底决策（§12 拍板项 3）风险陈述不完整，会导致 Owner 误判

- **设计断言**：`mechanism-design.md:347`（拍板项 3）把「放开桌面手开对话 v1 票据兜底」的代价只写成「接受**同机文件级读取者的理论窃票风险**」；`:48`（票据弱点）同样只写「票据存在于线程历史…理论上可窃取」。
- **漏写**：票据兜底的**前置**是「登记成功」（`:48`「登记成功后由桥接把…票据投进该对话上下文」），而登记前置（thread 绑定／标记证明）对桌面对话**同样受墙影响**（阻断 1）；且结果通知进桌面对话需写线程，对 `paginated` 线程不可用（阻断 3）。
- **后果**：Owner 被要求「放开／不放开」二选一时，缺「**墙下两条路对既有桌面对话都不通**」这一事实，决策依据不完整。**阻断。**

## 3. 建议发现（4 条）

### 建议 1｜§9 接口总表（15 项）与文中声称的能力不一致，缺 3 类端点

设计正文多处声称存在的能力在总表无对应项：

- `mechanism-design.md:220`：「破坏性操作（**撤销设备/对话、作废加入码**）单独显式端点」；`:132`「码可随时在管理面撤销」；`:273`–`276`（撤销 device／「其名下对话转 paused」／票据可轮换）。
- 但 `:285`–`300` 的 15 项中只有 `POST /v1/devices/register`、`POST /v1/devices/{id}/revoke`、`POST /v1/admin/join-codes`——**缺**：① 撤销/暂停**对话**端点；② 作废**加入码**端点；③ **RESULT/STATUS 回传提交**端点（`:169`–`170` 把 RESULT/STATUS 定义为消息类型，总表 `:300` 只列 `GET /v1/requests/{id}/result` 读结果，无提交）。

### 建议 2｜根密钥落点自相矛盾（§3 vs §8）

`mechanism-design.md:95`（§3 共同前提）：「Owner **在桥接上配置**一次根密钥 → `POST /v1/devices/register`」；`:272`（§8）：「根密钥…存 **Railway 环境变量（不入对话、不入桥接盘面）**」。两处对「系统里是否有第二个落点」表述不一致，需统一（若确为一次性内存输入，`:272` 应改为「不落桥接**盘面**／仅一次性输入」）。

### 建议 3｜元数据「全可见」对 §6 默认是放宽，正文未显式标注

`mechanism-design.md:84`–`88`（§2.3）与`:152`「首版单 Owner 租户内**花名册元数据全可见**」，相对 `plan-v1.md:129`（§6）「默认只公布**别名和必要状态**」是放宽。设计已在 D10/拍板项 2 披露，但正文未把「role/task/project/owner 全可见」显式标注为**对 §6 默认的越界授权决定**，复审时易被误读为符合默认。

### 建议 4｜链上限默认值性质与验收位

`mechanism-design.md:187`／D9（`:318`）「默认上限 3」为工程建议值（`:318` 自承「建议值非平台保证」）。建议按选人单 SD-4 补反向断言验收位（如「链深达上限必须被拒＋投『链上限已达』状态」），否则 M2 无法验收 §5.4。
